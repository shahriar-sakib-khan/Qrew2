# Data Field Categorization Rules

When implementing new features, tables, or data fields across the platform, you MUST categorize all fields into one of the following four categories. Mixing them up causes security flaws and UI bugs.

## Category 1: Configurable System Fields
- **Definition:** Natively built-in fields (e.g., \`projectName\`, \`clientName\`) that are present in the Custom Fields UI so users can configure if they are "Detailed", "Sensitive", or "Private".
- **Backend Enforcement:** The backend MUST read these toggles (\`org_settings.metadata.sysPrivateFields\`) and explicitly scrub the data from API payloads before sending it to the client if the user lacks permissions (e.g., non-owners cannot see Private fields).

## Category 2: Custom Fields
- **Definition:** Fields dynamically created by the user (stored in \`customFields\` JSONB column).
- **Backend Enforcement:** The backend MUST filter these out of the JSONB payload before sending it to the client if the user lacks the required PBAC permissions. Hiding them in the UI is not enough.

## Category 3: Immutable Auto-Fields (Metadata)
- **Definition:** Automatically generated by the system (e.g., \`createdAt\`, \`updatedAt\`, \`createdBy\`).
- **Implementation:** DO NOT put these in the Custom Fields schema builder. Users cannot configure them. They are toggled via Table View Settings (Columns dropdown).

## Category 4: Computed / Financial Fields
- **Definition:** Aggregated or sensitive computed fields (e.g., \`totalExpenses\`, \`totalRevenue\`).
- **Implementation:** DO NOT govern these via the Custom Fields "Sensitive" toggle. Financial data MUST be strictly wrapped in hardcoded PBAC components (e.g., \`<Can I="finance:view_expenses">\`). If a user lacks the hardcoded permission, the field must be completely hidden.
